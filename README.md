# To The Moon and Back -- A fun little site

This is my little headless CMS + Next baby for my photography and personal site.

Visit either:

- [jaisal.xyz](https://www.jaisal.xyz/)
- [jaisalfriedman.com](https://www.jaisalfriedman.com/)

## Architecture

- Next.js App Router renders the site statically and refreshes it with ISR.
- Payload CMS is embedded in the same app at `/admin`. Content lives in Postgres (Neon on Vercel, Docker locally) and photos in Vercel Blob, with responsive sizes generated by sharp.
- Pages read content in-process through Payload's Local API (`src/cms/*`); publishing in the admin revalidates the affected pages immediately.
- MUI and Tailwind style the site.

See [docs/architecture.md](docs/architecture.md) for details. Content moved here from Sanity; [docs/plans/sanity-to-payload-migration.md](docs/plans/sanity-to-payload-migration.md) records how.

## Development

Use Node.js 24 and Bun 1.4.2, plus Docker for the local database.

```bash
bun install --frozen-lockfile
cp .env.example .env
bun run dev-local
```

`dev-local` starts Postgres 18 in Docker, applies migrations, seeds sample content into an empty database, and starts the site on [localhost:3333](http://localhost:3333/). The admin is at [/admin](http://localhost:3333/admin). See [docs/development.md](docs/development.md) for content model changes and other workflows.

Type checks use the TypeScript 7 compiler (`typescript-compiler`). TypeScript 6 remains installed for tools that need the JavaScript compiler API, including Next.js and ESLint.

## Site Map

- `/` shows all photography collections sorted by most recent
- `/collections/[slug]` is a single photography series (a collection) with a title, date, description, etc. In the future, I may toy with a Next/Previous collection. The slug is a readable hyphenated string from the collection title.
- `/blog` and `/blog/[slug]` are blog posts
- `/about` is my personal static page about me
- `/admin` is the Payload CMS admin

## Deployment

Production deploys to Vercel when a stable GitHub release is published. The deployment workflow builds and deploys the release's immutable version tag. Automatic Git deployments from `main` are disabled; other branches retain Vercel previews.

Use Conventional Commit PR titles when squash merging into `main`: `feat:` proposes a minor release, `fix:` a patch, and `feat!:` a breaking release. Release-please maintains the version and changelog in a release PR. The dedicated release App enables auto-merge for verified, metadata-only release PRs once the normal required checks pass; no approval is required. After that merge, release-please publishes the tag and GitHub release, triggering production deployment.

Before merging this setup, configure the Actions secrets `VERCEL_TOKEN`, `VERCEL_ORG_ID`, and `VERCEL_PROJECT_ID` for the existing Vercel project. See [RELEASING.md](RELEASING.md) for secure credential setup, release App permissions, CI and tag protections, and deployment retries.

## Revalidation

Pages are generated at build time and revalidate every 10 minutes. Publishing, unpublishing, or deleting content in `/admin` revalidates the affected pages immediately through Payload hooks, so no webhooks or tunnels are involved. To force a refresh on both production domains, run `bun run revalidate <collection-slug>` with `REVALIDATE_SECRET` set.
